# SAVITR: Low-Powered Real-Time Adaptive Software-Defined Sonar Transmitter Payload for AUVs

SAVITR is a low-power, real-time adaptive software-defined sonar transmitter payload designed for Autonomous Underwater Vehicles (AUVs).

The system combines an offline Python physics engine with an ESP32-based embedded controller. The physics engine evaluates 10,000 discrete environmental states and pre-computes suitable sonar parameters. The ESP32 performs real-time environmental sensing and uses a 4D Lookup Table (LUT) to select the corresponding waveform, frequency, amplitude, and pulse duration.

This architecture shifts computationally expensive physics and waveform calculations offline, allowing the embedded system to perform lightweight real-time lookup and waveform transmission.

---

## System Architecture

The SAVITR system consists of two primary components:

### 1. Offline Physics Engine

The Python physics engine:

- Models underwater acoustic propagation.
- Evaluates absorption and scattering losses.
- Calculates transmission loss and required transmit levels.
- Selects appropriate waveform parameters.
- Generates pre-computed waveform samples.
- Evaluates a 4D environmental state space.
- Generates the ESP32 lookup-table header.

### 2. ESP32 Real-Time Controller

The ESP32 firmware:

- Reads environmental sensor inputs.
- Quantizes sensor values into discrete bins.
- Calculates the corresponding 4D LUT index.

- - Retrieves pre-computed sonar parameters from flash memory.
- Updates the OLED telemetry display when the environmental state changes.
- Provides the control interface for waveform transmission.

---

## ESP32 Firmware: Real-Time Adaptive Sonar Controller

The embedded firmware runs on an ESP32 microcontroller and maps real-time environmental measurements to the pre-computed sonar parameters generated by the offline physics engine.

### Workflow

The firmware operates through the following sequence:

1. **Sensor Ingestion**
   - Reads Depth, Turbidity, Temperature and Salinity inputs using the ESP32 ADC.

2. **State Quantization**
   - Converts the 12-bit ADC values from the range `0–4095` into 10 discrete bins from `0–9`.

3. **4D State Representation**
   - The four environmental parameters form a:

   `10 × 10 × 10 × 10 = 10,000 state`

   lookup space.

4. **4D Index Calculation**

   The unique LUT index is calculated using:

   ```text
   Index = (Depth × 1000) + (Turbidity × 100) + (Temperature × 10) + Salinity

      This produces an index from `0` to `9999`.

5. **LUT Fetch**
   - The corresponding waveform type, frequency, amplitude and duration are retrieved directly from the lookup table.

6. **Telemetry Update**
   - The OLED is updated only when the environmental state changes.
   - This avoids unnecessary I2C updates and reduces display flicker.

# Core Physics Models

The offline physics engine uses acoustic models to determine suitable sonar parameters for different underwater environmental conditions.

## 1. Acoustic Absorption — Francois-Garrison Model

The absorption coefficient is modeled as:

$$
\alpha_{abs} =
\frac{A_1 f^2}{f^2 + f_1^2}
+
\frac{A_2 P_2 f^2}{f^2 + f_2^2}
+
A_3 P_3 f^2
$$

where the coefficients depend on environmental properties such as temperature, salinity and pressure.

The model allows the physics engine to account for frequency-dependent acoustic absorption in seawater.

---

## 2. Turbidity Scattering — Rayleigh Approximation

Scattering loss caused by suspended particles is approximated as:

$$
\alpha_{scat}
=
K_{scat}
\cdot
\text{turbidity}
\cdot
\left(\frac{f}{f_{ref}}\right)^2
$$

This model represents the increase in scattering loss with turbidity and frequency.

---

## 3. Two-Way Transmission Loss

The total two-way transmission loss is represented using spreading and attenuation terms:

$$
TL =
40\log_{10}(R)
+
2(\alpha_{abs}+\alpha_{scat})
\left(\frac{R}{1000}\right)
$$

where:

- $R$ is the propagation range.
- $\alpha_{abs}$ is the absorption coefficient.
- $\alpha_{scat}$ is the scattering coefficient.

---

## 4. Active Sonar Equation

The required transmit level is estimated using:

$$
V_{req}
=
10^{
\frac{
(SNR_{min}+TL-TS+NL-SL_{ref})
}{20}
}
$$

The design target uses:

```text
SNRmin = 10 dB
'''

---

# Scattering Dominance Ratio

The relative contribution of scattering is represented by:

$$
\gamma =
\frac{L_{scat}}
{L_{abs}+L_{scat}}
$$

The resulting value is used by the physics engine when selecting the waveform strategy.

### High Scattering Conditions

For:

```text
γ ≥ 0.55
'''

the system selects the Barker-13 phase-coded waveform.

### Low Scattering Conditions

For:

```text
γ ≤ 0.45
'''

the system selects the Geometric Sweep waveform.

### Intermediate Conditions

For values between the two thresholds, the system uses an LFM chirp.

This allows waveform selection to adapt to the estimated acoustic environment.

# Hamming Window

The generated waveforms are multiplied by a Hamming window:

$$
w[n]
=
0.54
-
0.46
\cos
\left(
\frac{2\pi n}{N-1}
\right)
$$

Windowing reduces discontinuities at the beginning and end of the waveform.

Without windowing, abrupt signal transitions can introduce spectral leakage and higher sidelobe levels.

The Hamming window provides a compromise between:

- Main-lobe width
- Sidelobe suppression
- Range resolution

This makes it suitable for the prototype's waveform-generation approach.

# Low-Power Design

A key design objective of SAVITR is to move computationally expensive operations away from the real-time embedded controller.

Instead of calculating acoustic physics and waveform samples continuously on the ESP32:

1. Environmental states are evaluated offline.
2. Physics calculations are performed by Python.
3. Waveforms are generated offline.
4. The results are stored in `esp32_data.h`.
5. The ESP32 performs a lightweight LUT lookup during operation.

This reduces the computational workload of the microcontroller and supports low-power operation.

The waveform-generation architecture is intended to use the ESP32 I2S peripheral and DMA for efficient sample streaming.

# Engineering Design Considerations

## Why Use a LUT?

The embedded controller has limited computational and power resources.

The LUT approach allows complex calculations to be performed offline while keeping the real-time firmware lightweight.

Instead of repeatedly calculating:

- Trigonometric functions
- Logarithms
- Acoustic attenuation
- Scattering
- Waveform samples

the ESP32 performs a state calculation followed by a direct memory lookup.

---

## Why Pre-Compute Waveforms?

Pre-computed waveforms avoid repeatedly generating large waveform arrays during real-time operation.

The ESP32 can instead access the stored waveform data and use the appropriate transmission path for streaming.

---

## Why Use Windowing?

Abrupt waveform boundaries can introduce spectral leakage and sidelobes.

Applying a Hamming window smooths the waveform boundaries and reduces spectral leakage, providing a practical compromise between spectral performance and resolution.
